# T37 — Referential Integrity

> **Goal:** Learn how to prove that records referencing another entity actually point to a valid, appropriate, and temporally correct parent record.

## 1. Problem Recognition

Referential integrity answers:

    Does every relationship that claims to reference another entity actually resolve to a valid parent?

Examples:

    payment.customer_id → customer.customer_id
    order.product_id   → product.product_id
    transfer.account_id → account.account_id

A child record can be correctly typed, inside range, and inside the correct domain while still referencing nothing.

### Common failures

- Orphaned child records.
- Wrong parent identifier.
- Duplicate parent business keys.
- Parent record arrives after child record.
- Parent is soft-deleted.
- Parent belongs to another tenant.
- Parent exists but is not valid at event time.
- Child references deprecated parent state.
- Composite foreign key is only partially matched.
- Lookup joins accidentally multiply children.
- Missing reference data is treated as valid.

### Recognition questions

Before implementing referential validation, ask:

1. What is the parent entity?
2. What is the child entity?
3. What is the authoritative parent key?
4. Is the key a surrogate key, natural key, or business key?
5. Is the relationship one-to-one, many-to-one, or another cardinality?
6. Is tenant scope part of the key?
7. Can the child arrive before the parent?
8. Can the parent be deleted or deactivated?
9. Is the relationship valid for all time?
10. Does the parent need to be active at event time?
11. What happens when the parent is missing?
12. Should the child be quarantined, delayed, or rejected?

## 2. Concept and Reasoning

### 2.1 Parent and child

A parent owns or defines an entity referenced by another table.

Example:

    customer
       ↑
    payment

The payment references the customer.

### 2.2 Foreign key versus business validation

A database foreign key enforces existence at the database transaction boundary.

Pipeline referential validation may additionally need to handle:

- Historical validity.
- Soft deletion.
- Tenant scope.
- Source-system boundaries.
- Late-arriving dimensions.
- Quarantine and replay.

### 2.3 Existence is not enough

A parent may exist but still be invalid for the child.

Example:

    customer exists
    customer belongs to tenant B
    payment belongs to tenant A

The relationship is invalid despite the identifier existing.

### 2.4 Orphan records

An orphan is a child record with no valid parent.

Typical detection:

    child LEFT JOIN parent
    WHERE parent.key IS NULL

Use a reliable parent key column for the NULL test.

### 2.5 Why orphan records occur

Common causes:

- Arrival-order differences.
- Failed parent ingestion.
- Incorrect key mapping.
- Source-system deletion.
- Partial batch processing.
- Schema changes.
- Incorrect tenant scoping.
- Parent records filtered out upstream.

### 2.6 Natural keys

A natural key has business meaning.

Examples:

    customer_number
    country_code
    account_number

Natural keys can change or collide across systems.

### 2.7 Surrogate keys

A surrogate key is generated by the data platform.

Examples:

    customer_sk
    product_sk

Fact records should generally resolve to the correct surrogate key through a governed business-key relationship.

### 2.8 Business keys

A business key identifies an entity according to business semantics.

Example:

    customer_id

Before enforcing a relationship, confirm the business key's uniqueness and scope.

### 2.9 Composite keys

Sometimes the relationship requires multiple columns:

    tenant_id + customer_id

Checking only `customer_id` can create cross-tenant relationships.

### 2.10 Tenant-scoped referential integrity

Validate:

    child.tenant_id = parent.tenant_id
    child.customer_id = parent.customer_id

Both conditions are part of the relationship.

### 2.11 Parent uniqueness

Referential validation assumes the parent key identifies one intended parent.

If the parent contains:

    customer_id = 100
    customer_id = 100

a child lookup can multiply rows or become ambiguous.

Parent uniqueness must therefore be validated separately.

### 2.12 Referential integrity and JOIN fan-out

A parent lookup should normally be many-to-one from child to parent.

If one child matches multiple parents, the relationship is ambiguous.

Do not hide the issue with `DISTINCT`.

### 2.13 Existence versus state

A parent can be:

    active
    inactive
    deleted
    suspended

Decide which states permit child relationships.

### 2.14 Soft deletion

Soft deletion keeps the parent row but marks it inactive.

Existence validation alone may pass while business validity fails.

### 2.15 Temporal referential integrity

A child may need a parent that was valid when the event occurred.

Example:

    payment.event_time
    customer.effective_from
    customer.effective_to

The correct parent is the version active at the child event time.

### 2.16 Slowly changing dimensions

SCD Type 2 creates multiple historical parent versions.

A child relationship must select the correct version rather than simply the latest row.

### 2.17 Late-arriving parents

An event may arrive before its parent dimension.

This is not always an invalid business relationship.

Possible policies:

    wait
    quarantine
    use inferred member
    load parent first

Choose deliberately.

### 2.18 Inferred members

Some dimensional systems create a temporary parent record when a fact arrives first.

The inferred record must be clearly marked and later reconciled with the real parent.

### 2.19 Late-arriving children

The parent may already exist while child events arrive late.

This is usually easier, but historical validity still matters if the parent changed over time.

### 2.20 Parent deletion

Deleting a parent can affect many children.

Possible policies:

    RESTRICT
    CASCADE
    SET NULL
    soft delete

Production analytics pipelines should choose based on business semantics, not convenience.

### 2.21 Cascading deletion risk

An accidental cascade can remove large portions of downstream data.

For analytical systems, prefer controlled deletion workflows and explicit impact analysis.

### 2.22 SET NULL risk

Replacing a missing parent key with NULL may preserve the child row but destroy relationship information.

Use only when NULL has defined semantics.

### 2.23 Parent key mutation

If a natural key changes, dependent children can break unless the system supports key history or controlled migration.

Surrogate-key architectures can reduce this risk.

### 2.24 Referential integrity and source systems

Different source systems may use different identifiers.

Example:

    CRM customer_id
    Payments customer_id
    Warehouse customer_sk

Map identifiers through governed cross-reference data.

### 2.25 Cross-reference tables

A cross-reference can contain:

    source_system
    source_customer_id
    canonical_customer_id
    effective_from
    effective_to

This allows source-specific identifiers to resolve to a canonical entity.

### 2.26 Missing cross-reference

If a source identifier cannot be mapped, classify:

    UNMAPPED_PARENT_KEY

Do not guess the parent.

### 2.27 Referential integrity and domain validation

Domain validation checks whether a value belongs to an allowed set.

Referential integrity checks whether a value resolves to the correct entity relationship.

A foreign key can be a domain of identifiers, but the relationship carries additional semantics.

### 2.28 Referential integrity and range validation

An ID can be numerically valid while pointing to no parent.

Range validation cannot replace relationship validation.

### 2.29 Referential integrity and required fields

A required parent key can be present while still being invalid.

Example:

    customer_id = 123

does not prove customer 123 exists.

### 2.30 Referential integrity and aggregation

Orphan facts can produce totals that cannot be attributed to a parent.

Decide whether unattributed facts:

    are quarantined
    use an explicit unknown member
    remain in a separate reconciliation population

### 2.31 Unknown dimension member

An explicit unknown member can preserve fact rows when business reporting requires complete fact ingestion.

Example:

    customer_sk = -1

This is not the same as silently inventing a customer.

### 2.32 Unknown member governance

If using an unknown member, track:

    reason
    original key
    first_seen_at
    resolution_status

Otherwise the unknown bucket can become permanent data loss.

### 2.33 Referential integrity and event time

Relationship validity can depend on event time rather than ingestion time.

Always define which clock controls the relationship.

### 2.34 Referential integrity and snapshots

Snapshot-based parent tables require alignment between child and parent snapshots.

Joining a child from one snapshot to a parent from another can create historically incorrect relationships.

### 2.35 Referential integrity and incremental processing

Incremental pipelines may process children before new parent records.

Track unresolved references and replay them after parent ingestion.

### 2.36 Referential integrity and idempotence

Replaying a child should resolve to the same parent unless reference data intentionally changed.

Deterministic parent selection is essential.

### 2.37 Referential integrity and data quality

Track both:

    relationship validity
    parent quality

A child can resolve to a parent that itself contains invalid data.

### 2.38 Referential integrity and security boundaries

Tenant or authorization boundaries can be part of relationship correctness.

Do not allow an identifier from one security scope to resolve to an entity in another scope.

### 2.39 Referential integrity and schema evolution

Renaming identifiers, changing key formats, or introducing new key namespaces can break relationships without changing table structure.

Monitor relationship failure rates during migrations.

### 2.40 Fail-open versus fail-closed

When the parent dataset is unavailable, decide whether to:

    stop
    quarantine
    retry
    use a verified snapshot

Do not interpret an unavailable parent table as proof that no parent exists.

## 3. Implementation

### 3.1 Define the relationship contract

Example:

    payment.customer_id
        references customer.customer_id
        same tenant_id
        parent must exist
        parent must be active at event_time

### 3.2 Parent table

    CREATE TABLE customer (
        customer_id BIGINT PRIMARY KEY,
        tenant_id BIGINT NOT NULL,
        status TEXT NOT NULL,
        effective_from TIMESTAMPTZ NOT NULL,
        effective_to TIMESTAMPTZ
    );

### 3.3 Child table

    CREATE TABLE payment (
        payment_id BIGINT PRIMARY KEY,
        tenant_id BIGINT NOT NULL,
        customer_id BIGINT NOT NULL,
        event_time TIMESTAMPTZ NOT NULL,
        amount NUMERIC(20,4) NOT NULL
    );

### 3.4 Basic orphan detection

    SELECT p.payment_id, p.customer_id
    FROM payment p
    LEFT JOIN customer c
      ON c.customer_id = p.customer_id
    WHERE c.customer_id IS NULL;

Use the parent's non-nullable key for the existence test.

### 3.5 Tenant-scoped relationship

    SELECT p.payment_id
    FROM payment p
    LEFT JOIN customer c
      ON c.tenant_id = p.tenant_id
     AND c.customer_id = p.customer_id
    WHERE c.customer_id IS NULL;

This prevents cross-tenant matches.

### 3.6 Detect ambiguous parents

Before trusting the relationship, check:

    SELECT tenant_id, customer_id, COUNT(*)
    FROM customer
    GROUP BY tenant_id, customer_id
    HAVING COUNT(*) > 1;

If multiple current parents are possible, the relationship needs an additional rule.

### 3.7 Active-parent validation

    LEFT JOIN customer c
      ON c.tenant_id = p.tenant_id
     AND c.customer_id = p.customer_id
     AND c.status = 'active'

Use this only if active state is part of the relationship contract.

### 3.8 Temporal relationship

    LEFT JOIN customer c
      ON c.tenant_id = p.tenant_id
     AND c.customer_id = p.customer_id
     AND p.event_time >= c.effective_from
     AND (c.effective_to IS NULL OR p.event_time < c.effective_to)

This resolves the parent version valid at event time.

### 3.9 Detect multiple temporal matches

Historical parent records should not overlap.

Detect overlapping effective intervals before using them for deterministic lookup.

### 3.10 Parent uniqueness test

    SELECT tenant_id, customer_id
    FROM customer
    GROUP BY tenant_id, customer_id
    HAVING COUNT(*) > 1;

For SCD Type 2, uniqueness should be evaluated at the correct temporal grain rather than globally.

### 3.11 Cross-reference table

    CREATE TABLE customer_xref (
        source_system TEXT NOT NULL,
        source_customer_id TEXT NOT NULL,
        customer_id BIGINT NOT NULL,
        effective_from TIMESTAMPTZ NOT NULL,
        effective_to TIMESTAMPTZ,
        PRIMARY KEY (source_system, source_customer_id, effective_from)
    );

Resolve source identifiers through this table before joining to the canonical parent.

### 3.12 Detect unmapped identifiers

    SELECT p.payment_id, p.source_customer_id
    FROM payment_raw p
    LEFT JOIN customer_xref x
      ON x.source_system = p.source_system
     AND x.source_customer_id = p.source_customer_id
    WHERE x.customer_id IS NULL;

Classify these separately from missing canonical customers.

### 3.13 Validation result table

    CREATE TABLE referential_integrity_failure (
        batch_id TEXT NOT NULL,
        child_id TEXT NOT NULL,
        relationship_name TEXT NOT NULL,
        parent_key_hash TEXT,
        failure_code TEXT NOT NULL,
        detected_at TIMESTAMPTZ NOT NULL
    );

Hash or omit sensitive identifiers when full values are not required for operations.

### 3.14 Failure categories

Useful categories include:

    MISSING_PARENT
    WRONG_TENANT
    INACTIVE_PARENT
    AMBIGUOUS_PARENT
    UNMAPPED_PARENT_KEY
    TEMPORALLY_INVALID_PARENT
    REFERENCE_DATA_UNAVAILABLE

### 3.15 Python lookup validation

    def validate_parent(child, parent_keys):
        key = (child['tenant_id'], child['customer_id'])
        if key not in parent_keys:
            return 'MISSING_PARENT'
        return None

For large datasets, use indexed database joins or vectorized structures rather than per-row remote lookups.

### 3.16 Python parent map

Conceptually:

    parent_map = {
        (1, 100): {'status': 'active'},
        (1, 101): {'status': 'active'},
    }

Use this only when the reference dataset fits safely in memory and freshness requirements allow it.

### 3.17 Pandas validation

Conceptually:

    merged = children.merge(
        parents[['tenant_id', 'customer_id']],
        on=['tenant_id', 'customer_id'],
        how='left',
        indicator=True,
    )

Then identify records with `_merge == 'left_only'`.

### 3.18 Avoiding fan-out

Before joining, verify the parent relation is unique at the required grain.

Do not use:

    DISTINCT

to hide multiple parent matches.

### 3.19 Quarantine branch

Conceptually:

    child records
          ↓
    referential validation
       ├── resolved → trusted child
       └── unresolved → quarantine

Store enough metadata to replay after the parent becomes available.

### 3.20 Retryable versus permanent failures

Retryable:

    parent not loaded yet
    reference service unavailable

Potentially permanent:

    malformed key
    nonexistent business entity
    invalid tenant relationship

Classify failures so retry workers do not repeatedly process permanent errors.

### 3.21 Unknown member strategy

If the warehouse requires complete fact ingestion, route unresolved children to an explicit unknown parent member.

Store:

    original_parent_key
    unknown_reason
    first_seen_at
    resolution_status

### 3.22 Resolution workflow

When a parent arrives:

    find unresolved children
        ↓
    resolve parent
        ↓
    update relationship
        ↓
    remove from unresolved state
        ↓
    reconcile downstream outputs

### 3.23 Database foreign key

For transactional systems, a foreign key can enforce basic existence:

    FOREIGN KEY (customer_id)
    REFERENCES customer(customer_id)

This is strong protection but does not replace temporal, tenant-scoped, or source-mapping validation.

### 3.24 Delete behavior

Choose deletion semantics deliberately:

    RESTRICT
    CASCADE
    SET NULL

For analytics, soft deletion and controlled archival often provide safer auditability than uncontrolled cascading deletion.

### 3.25 Reconciliation

Track:

    child_rows
    resolved_rows
    unresolved_rows
    ambiguous_rows
    retryable_rows

and verify:

    child_rows = resolved + unresolved + ambiguous + explicitly_exempt

when categories are mutually exclusive.

## 4. Testing

### 4.1 Valid parent

Create a child whose parent exists.

Expected:

    RESOLVED

### 4.2 Missing parent

Create a child referencing a nonexistent parent.

Expected:

    MISSING_PARENT

### 4.3 Wrong tenant

Create a parent with the same customer ID under another tenant.

Expected:

    WRONG_TENANT

not a successful match.

### 4.4 Duplicate parent

Create multiple current parents for the same relationship key.

Expected:

    AMBIGUOUS_PARENT

### 4.5 Inactive parent

Create a parent that exists but is inactive.

Expected result should follow the relationship contract.

### 4.6 Temporal parent

Create multiple parent versions with different effective intervals.

Verify the child resolves to the version active at event time.

### 4.7 Temporal boundary

Test exactly at:

    effective_from
    effective_to

Verify half-open interval semantics.

### 4.8 Overlapping parent versions

Create overlapping effective intervals.

Expected:

    ambiguous relationship

rather than nondeterministic selection.

### 4.9 Late-arriving parent

Process the child before the parent.

Expected:

    retryable unresolved state

Then load the parent and replay.

Expected:

    resolved child

### 4.10 Unmapped source identifier

Provide a source key with no cross-reference mapping.

Expected:

    UNMAPPED_PARENT_KEY

### 4.11 Parent deletion

Delete or deactivate a referenced parent.

Verify configured delete behavior and downstream impact.

### 4.12 Unknown member

Route an unresolved child to an explicit unknown member.

Verify:

    original key retained
    reason retained
    child count preserved

### 4.13 Idempotence

Run referential validation twice.

Expected:

    same classification
    no duplicate quarantine records

### 4.14 Fan-out protection

Create duplicate parent records.

Verify the validation stage detects ambiguity rather than multiplying children.

### 4.15 Composite key

Change one component of a composite relationship.

Expected:

    relationship fails

### 4.16 Snapshot mismatch

Use a parent snapshot from a different effective period.

Expected:

    temporal or snapshot mismatch detected

### 4.17 Reference outage

Make the parent dataset unavailable.

Expected:

    REFERENCE_DATA_UNAVAILABLE

not MISSING_PARENT for every child.

### 4.18 Reconciliation

Verify:

    input = resolved + unresolved + ambiguous + explicit exemptions

### 4.19 Replay

Process unresolved children again after the parent arrives.

Expected:

    resolved count increases
    unresolved count decreases
    no duplicate child records

## 5. Observability

### Core metrics

| Metric | Meaning |
|---|---|
| `referential_input_rows` | Child records checked |
| `referential_resolved_rows` | Records with valid parents |
| `referential_missing_parent` | No parent found |
| `referential_wrong_scope` | Parent exists outside required scope |
| `referential_inactive_parent` | Parent exists but is not allowed |
| `referential_ambiguous_parent` | Multiple parents match |
| `referential_unmapped_key` | Source key cannot be mapped |
| `referential_temporal_failure` | Parent invalid at child event time |
| `referential_reference_unavailable` | Parent reference unavailable |

### Resolution rate

Monitor:

    resolved / input

Track by:

- Relationship.
- Source.
- Tenant.
- Product.
- Batch.

### Orphan rate

A rising orphan rate can indicate:

- Parent ingestion lag.
- Parent pipeline failure.
- Key mapping changes.
- Source deletions.
- Incorrect joins.

### Parent uniqueness

Monitor duplicate current parent keys.

Any increase can make child resolution ambiguous.

### Late-arrival backlog

Track:

- Unresolved children.
- Oldest unresolved child.
- Retry attempts.
- Time since first seen.
- Resolution rate.

### Reference freshness

Monitor the age of the parent dataset.

A stale parent snapshot can produce false missing-parent or temporal failures.

### Unknown-member usage

If using an unknown member, monitor its population.

A permanently growing unknown bucket usually indicates unresolved reference problems.

## 6. Intentional Failure

### Failure 1 — Ignore tenant scope

Join only on customer ID.

Expected symptom:

- Cross-tenant relationships.

Recovery:

Include tenant scope in the relationship key.

### Failure 2 — Duplicate parent

Create two parents with the same active key.

Expected symptom:

- Child fan-out or ambiguous resolution.

Recovery:

Repair parent uniqueness and prevent publication of ambiguous relationships.

### Failure 3 — Latest-parent lookup for historical child

Always select the current parent.

Expected symptom:

- Historical facts acquire incorrect parent attributes.

Recovery:

Use event-time effective-dated selection.

### Failure 4 — Missing parent treated as permanent

Reject every unresolved child immediately.

Expected symptom:

- Legitimate late-arriving children are lost.

Recovery:

Classify retryable missing parents and replay them.

### Failure 5 — Missing parent treated as valid

Allow unmatched children into trusted data without an explicit unknown strategy.

Expected symptom:

- Broken attribution.

Recovery:

Quarantine or use a governed unknown member.

### Failure 6 — `DISTINCT` hides fan-out

Deduplicate after a many-to-many parent join.

Expected symptom:

- Ambiguity disappears from metrics but relationship semantics remain wrong.

Recovery:

Validate parent uniqueness before joining.

### Failure 7 — Reference outage classified as missing parents

Make the parent dataset unavailable.

Expected symptom:

- Every child appears orphaned.

Recovery:

Detect reference availability separately.

### Failure 8 — Unsafe cascade

Delete a parent with dependent children using uncontrolled cascade behavior.

Expected symptom:

- Large unexpected data loss.

Recovery:

Restore from controlled snapshots and change delete policy.

## 7. Recovery

### Recovery sequence

1. Preserve the child records.
2. Identify the relationship and key.
3. Check parent availability.
4. Check key mapping.
5. Check tenant scope.
6. Check parent uniqueness.
7. Check parent state.
8. Check event-time validity.
9. Classify retryable versus permanent failure.
10. Repair the parent or mapping.
11. Replay affected children.
12. Reconcile downstream outputs.
13. Add regression coverage.

### Recovering from parent ingestion lag

1. Keep unresolved children in a retryable state.
2. Load the parent.
3. Re-run relationship validation.
4. Publish newly resolved records.
5. Reconcile the backlog.

### Recovering from key mapping changes

1. Identify affected source identifiers.
2. Preserve original keys.
3. Correct cross-reference mappings.
4. Reprocess affected children.
5. Validate no cross-tenant relationships were introduced.

### Recovering from duplicate parents

1. Identify duplicate parent keys.
2. Determine the authoritative parent.
3. Repair the parent dimension.
4. Re-run ambiguous children.
5. Reconcile any previously multiplied outputs.

### Recovering from historical relationship errors

1. Identify affected event-time range.
2. Resolve the correct parent versions.
3. Rebuild affected partitions.
4. Recalculate dependent aggregates.
5. Compare before and after populations.

## 8. Production Tools You Should Know

### 1. PostgreSQL

PostgreSQL provides foreign keys, unique constraints, indexes, joins, and transaction-level integrity enforcement.

Understand database referential integrity before building application-level relationship checks.

### 2. dbt

dbt relationship tests can verify that child keys resolve to parent records.

Use them alongside model-specific temporal and scope logic when basic relationships are insufficient.

### 3. Great Expectations

Great Expectations can validate relationship and lookup expectations as part of data-quality workflows.

Use the framework to operationalize the relationship contract, not to replace understanding of key semantics.

## 10. Common Mistakes

### Mistake 1 — Checking only key presence

A present key does not prove the relationship is valid.

### Mistake 2 — Ignoring tenant scope

Global IDs can create cross-tenant relationships.

### Mistake 3 — Ignoring parent uniqueness

Duplicate parents can multiply child rows.

### Mistake 4 — Selecting the latest parent

Historical children need historically valid parents.

### Mistake 5 — Rejecting every late parent

Arrival order is not the same as business validity.

### Mistake 6 — Treating missing reference data as missing parents

Reference outage and true orphan records are different failures.

### Mistake 7 — Using DISTINCT to hide fan-out

Deduplication does not repair an ambiguous relationship.

### Mistake 8 — No replay mechanism

Late-arriving parents require deterministic reprocessing.

### Mistake 9 — Permanent unknown member

Unknown members need resolution monitoring.

### Mistake 10 — Unsafe cascades

Parent deletion can affect large downstream populations.

### Mistake 11 — No raw-key preservation

Without the original key, relationship repair becomes difficult.

### Mistake 12 — No relationship observability

Orphan and ambiguity rates should be measurable per relationship.

## 12. What You Learned

Referential integrity protects relationships between datasets. A child record is not trustworthy merely because its parent key is present or correctly typed.

The production workflow is:

    DEFINE RELATIONSHIP
         ↓
    VALIDATE KEY SEMANTICS
         ↓
    RESOLVE PARENT
         ↓
    CHECK SCOPE / STATE / TIME
         ↓
    CLASSIFY MISSING OR AMBIGUOUS RELATIONSHIPS
         ↓
    QUARANTINE OR RETRY
         ↓
    PUBLISH RESOLVED RECORDS
         ↓
    MONITOR ORPHANS AND REFERENCE HEALTH

> **Referential integrity is more than “the key exists”; production pipelines must prove that the correct parent exists, in the correct scope, state, and time, with deterministic recovery when it does not.**
