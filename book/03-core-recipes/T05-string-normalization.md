# T05 — String Normalization\n\n## 1. Problem Recognition\n\nProduction pipelines receive text in inconsistent representations:\n\n    " Farhan "\n    "FARHAN"\n    "farhan  khan"\n    " pk "\n    "José"\n\nThese values may represent the same business value, different values, or invalid data. String normalization creates a controlled canonical representation without destroying meaning.\n\nCore rule:\n\n> Normalize only what the field contract permits.\n\n## 2. What You Are Building\n\n    raw text\n       |\n       v\n    classify state\n       |\n       v\n    Unicode normalization\n       |\n       v\n    field-specific normalization\n       |\n       v\n    semantic validation\n       |\n       +----------+\n       |          |\n       v          v\n     valid     invalid\n       |          |\n       v          v\n    staging   quarantine/fail\n\nThe goal is consistency while preserving business meaning.\n\n## 3. Learning Objectives\n\nBy the end of this recipe you should be able to:\n\n1. Distinguish normalization from validation.\n2. Trim and normalize whitespace safely.\n3. Understand Unicode normalization.\n4. Apply case normalization by field.\n5. Normalize codes and identifiers conservatively.\n6. Handle names, emails, phone numbers, and free text appropriately.\n7. Build canonical comparison keys.\n8. Keep opaque values such as passwords and tokens untouched.\n9. Test Unicode, punctuation, and edge cases.\n10. Verify idempotence and determinism.\n11. Observe normalization changes.\n12. Recover from incorrect normalization.\n\n## 4. Normalization vs Validation\n\nNormalization converts an accepted representation into a canonical representation.\n\nExample:\n\n    "  PK  " -> "PK"\n\nValidation asks whether the resulting value is allowed:\n\n    "PK" -> valid country code\n    "P@K" -> invalid country code\n\nDo not use normalization to turn invalid data into apparently valid data.\n\n## 5. Field-Specific Rules\n\n| Field | Possible normalization |\n|---|---|\n| Name | Unicode NFC, trim, controlled whitespace |\n| Country code | trim + uppercase |\n| Currency code | trim + uppercase |\n| UUID | parse + canonical format |\n| Email | trim; case handling according to contract |\n| Phone | standards-aware parsing |\n| External ID | preserve unless specification allows normalization |\n| Free text | usually minimal normalization |\n| Password | do not normalize generically |\n\nThere is no universally safe normalize_string function for every field.\n\n## 6. Trim Outer Whitespace\n\nPython:\n\n    def trim_text(value):\n        if value is None:\n            return None\n        if not isinstance(value, str):\n            raise TypeError("EXPECTED_STRING")\n        return value.strip()\n\nExample:\n\n    "  Farhan  " -> "Farhan"\n\nTrimming should be a field policy, not an assumption for every possible string.\n\n## 7. Internal Whitespace\n\nThese representations differ:\n\n    "Farhan Khan"\n    "Farhan  Khan"\n    "Farhan\tKhan"\n\nFor ordinary human names, a contract may allow whitespace collapse:\n\n    import re\n    value = re.sub(r"\s+", " ", value.strip())\n\nDo not apply this to arbitrary free text where whitespace can be meaningful.\n\n## 8. Empty Strings\n\nAfter trimming:\n\n    ""\n    "   "\n\nmay become equivalent representations.\n\nWhether an empty result becomes NULL is a T03 null-policy decision. Do not silently mix string normalization with missing-value policy.\n\n## 9. Case Normalization\n\nCase rules must be field-specific.\n\nExamples:\n\n    country code -> uppercase\n    currency code -> uppercase\n    UUID text -> canonical representation\n    password -> preserve\n    display name -> preserve unless presentation policy says otherwise\n\nDo not lowercase every string in a dataset.\n\n## 10. Lower vs Casefold\n\nPython provides lower() and casefold().\n\ncasefold() is designed for Unicode-aware caseless comparison and can be more aggressive than lower(). It is useful for derived comparison keys when the contract requires Unicode-aware matching.\n\nDo not replace stored display text with a casefolded value unless that is explicitly required.\n\n## 11. Unicode Normalization\n\nUnicode can represent visually equivalent text using different underlying sequences.\n\nPython:\n\n    import unicodedata\n    value = unicodedata.normalize("NFC", value)\n\nCommon forms are:\n\n    NFC\n    NFD\n    NFKC\n    NFKD\n\nNFC is often appropriate for canonical Unicode representation. NFKC performs compatibility normalization and can change characters that are only compatibility-equivalent.\n\nDo not use NFKC globally without understanding its effects on identifiers and business text.\n\n## 12. Unicode-Aware Normalizer\n\n    import unicodedata\n\n    def normalize_unicode(value):\n        if value is None:\n            return None\n        if not isinstance(value, str):\n            raise TypeError("EXPECTED_STRING")\n        return unicodedata.normalize("NFC", value)\n\nFollow Unicode and protocol requirements for security-sensitive identifiers rather than inventing custom rules.\n\n## 13. Do Not Force ASCII\n\nA transformation such as ASCII encoding with errors ignored can silently delete meaningful characters.\n\nExample risk:\n\n    José -> Jose\n\nThat may be acceptable for a derived search key in a specific system, but it should not silently replace the canonical business value.\n\nPreserve Unicode unless the target contract explicitly requires another representation.\n\n## 14. Diacritics\n\nNames such as:\n\n    José\n    Łukasz\n    François\n\ncontain meaningful characters.\n\nDo not remove diacritics merely to make strings look simpler. If accent-insensitive matching is required, create an explicit derived matching strategy.\n\n## 15. Names\n\nA conservative name normalizer can be:\n\n    def normalize_name(value):\n        if value is None:\n            return None\n        value = unicodedata.normalize("NFC", value)\n        value = value.strip()\n        return re.sub(r"\s+", " ", value)\n\nDo not automatically title-case names or remove apostrophes and hyphens.\n\nExamples that may carry meaning:\n\n    O'Connor\n    Anne-Marie\n    McDONALD\n\n## 16. Email Addresses\n\nA safe baseline is to remove accidental surrounding whitespace.\n\n    " user@example.com " -> "user@example.com"\n\nFurther case handling depends on the application's identity contract. Do not assume that every email component can safely be changed without consulting the system's rules.\n\nNormalization does not replace email validation.\n\n## 17. Phone Numbers\n\nPhone numbers should not be normalized by arbitrary punctuation deletion alone.\n\nPrefer standards-aware parsing that understands country context, prefixes, and extensions.\n\nDo not assume:\n\n    remove every non-digit character\n\nis universally correct.\n\n## 18. Country and Currency Codes\n\nFor a field explicitly defined as a code:\n\n    value = value.strip().upper()\n\nThen validate against the supported code set.\n\nNormalization:\n\n    " pk " -> "PK"\n\nValidation:\n\n    "PK" -> supported\n    "P@K" -> invalid\n\nNormalization must not manufacture a valid code from an invalid value.\n\n## 19. Identifiers\n\nIdentifiers require conservative treatment.\n\nPotentially safe:\n\n    trim\n    protocol-defined Unicode normalization\n    protocol-defined case normalization\n\nPotentially dangerous:\n\n    punctuation removal\n    transliteration\n    arbitrary case changes\n    whitespace deletion\n\nAn identifier such as AC-1001 should not become AC1001 unless the identifier specification says the separator is non-semantic.\n\n## 20. UUIDs\n\nParse UUIDs instead of performing generic string cleanup.\n\n    from uuid import UUID\n\n    def normalize_uuid(value):\n        if value is None:\n            return None\n        return str(UUID(str(value).strip()))\n\nThis both validates the UUID and produces a canonical textual form.\n\n## 21. URLs\n\nURLs should be parsed according to URL semantics.\n\nDo not blindly lowercase the entire URL, remove slashes, or remove punctuation. Hostnames and paths do not necessarily have identical case semantics.\n\nNormalize only components for which the protocol defines canonicalization.\n\n## 22. Free Text\n\nFree text normally deserves minimal normalization.\n\nPossible baseline:\n\n    Unicode NFC\n    outer whitespace trimming\n\nAvoid global:\n\n    lowercasing\n    punctuation removal\n    whitespace collapse\n\nunless the field contract explicitly requires them.\n\n## 23. Canonical Value vs Comparison Key\n\nWhen aggressive normalization is needed for search or matching, separate the canonical value from the derived comparison key.\n\nExample:\n\n    display_name = "José García"\n    name_match_key = derived canonical comparison value\n\nA comparison key can use casefolding and controlled whitespace rules without destroying the original business representation.\n\n## 24. Canonical Comparison Key\n\n    def build_name_key(value):\n        value = unicodedata.normalize("NFC", value)\n        value = value.strip()\n        value = re.sub(r"\s+", " ", value)\n        return value.casefold()\n\nTreat the key as derived data. Version the rule if it affects deduplication or identity.\n\n## 25. Punctuation\n\nPunctuation can be semantic or merely formatting.\n\nExamples:\n\n    O'Connor\n    AC-1001\n    v1.2.3\n    user@example.com\n\nDo not remove punctuation globally.\n\nIf a field specification says separators are non-semantic, document exactly which characters are removed.\n\n## 26. Invisible and Control Characters\n\nUnexpected text can contain:\n\n    tabs\n    newlines\n    non-breaking spaces\n    control characters\n    zero-width characters\n\nThese can cause equality, search, and deduplication problems.\n\nDetect them where relevant and define field-specific handling. Do not globally delete every invisible character from all text.\n\n## 27. Generic Normalizer\n\n    import re\n    import unicodedata\n\n    def normalize_text(\n        value,\n        *,\n        unicode_form="NFC",\n        trim=True,\n        collapse_whitespace=False,\n        case=None,\n    ):\n        if value is None:\n            return None\n        if not isinstance(value, str):\n            raise TypeError("EXPECTED_STRING")\n\n        value = unicodedata.normalize(unicode_form, value)\n\n        if trim:\n            value = value.strip()\n\n        if collapse_whitespace:\n            value = re.sub(r"\s+", " ", value)\n\n        if case == "lower":\n            value = value.lower()\n        elif case == "upper":\n            value = value.upper()\n        elif case == "casefold":\n            value = value.casefold()\n        elif case is not None:\n            raise ValueError("INVALID_CASE_POLICY")\n\n        return value\n\nThis is a mechanism, not a universal policy.\n\n## 28. Field Policy\n\n    STRING_POLICIES = {\n        "country": {\n            "trim": True,\n            "case": "upper",\n            "collapse_whitespace": False,\n        },\n        "currency": {\n            "trim": True,\n            "case": "upper",\n            "collapse_whitespace": False,\n        },\n        "name": {\n            "trim": True,\n            "case": None,\n            "collapse_whitespace": True,\n        },\n        "description": {\n            "trim": True,\n            "case": None,\n            "collapse_whitespace": False,\n        },\n    }\n\nExplicit field policies make transformations reviewable.\n\n## 29. Validation After Normalization\n\nExample:\n\n    SUPPORTED_COUNTRIES = {"PK", "DE", "FR"}\n\n    def validate_country(value):\n        if value not in SUPPORTED_COUNTRIES:\n            raise ValueError("INVALID_COUNTRY")\n        return value\n\nSequence:\n\n    " pk "\n       ↓\n    "PK"\n       ↓\n    validate\n       ↓\n    accepted\n\nDo not turn invalid values into valid ones through aggressive cleanup.\n\n## 30. Idempotence\n\nA canonical normalizer should usually be idempotent:\n\n    normalize(normalize(x)) == normalize(x)\n\nExample:\n\n    "  pk  "\n        ↓\n      "PK"\n        ↓\n      "PK"\n\nIdempotence makes retries, replay, and backfills safer.\n\n## 31. Determinism\n\nGiven the same:\n\n    input\n    normalization policy\n    software version\n\nthe result should be deterministic.\n\nA canonical normalizer should not depend on current time or random state.\n\n## 32. Normalization and Joins\n\nA join can fail because:\n\n    left.country = "PK"\n    right.country = " pk "\n\nNormalize both sides according to the same contract before joining.\n\nDo not normalize only one side.\n\n## 33. Normalization and Hashing\n\nIf a normalized value is used to build a hash key, normalization must happen before hashing.\n\nOtherwise:\n\n    hash("PK") != hash(" pk ")\n\neven if the business contract treats them as equivalent.\n\nThe normalization policy therefore becomes part of the key contract.\n\n## 34. Opaque Values\n\nDo not generically normalize:\n\n    passwords\n    API keys\n    access tokens\n    signatures\n    opaque idempotency keys\n\nThese values are often exact sequences. Changing case, whitespace, or Unicode representation can invalidate them or create collisions.\n\n## 35. Database Considerations\n\nPostgreSQL text types support Unicode, but storage type alone does not define business normalization.\n\nWhen normalized values participate in uniqueness or joins, consider:\n\n    canonical representation\n    collation\n    indexes\n    unique constraints\n    expression or derived keys\n\nPython equality and database comparison behavior should not be assumed identical.\n\n## 36. Observability\n\nTrack:\n\n    string_values_processed_total\n    string_values_changed_total\n    normalization_errors_total\n    validation_failures_total\n    normalization_change_rate\n\nUseful dimensions:\n\n    source\n    dataset\n    field\n    normalization_rule\n    policy_version\n    pipeline_run\n\nDo not log sensitive raw values merely to explain a normalization change.\n\n## 37. Change Rate\n\n    normalization_change_rate = changed_values / processed_values\n\nExample:\n\n    processed = 1,000,000\n    changed = 40,000\n    change rate = 4%\n\nA sudden increase can indicate a producer formatting change, encoding issue, new source, or legitimate source behavior.\n\n## 38. Testing Strategy\n\nFor every important field test:\n\n    None\n    empty\n    whitespace\n    leading/trailing whitespace\n    repeated whitespace\n    uppercase/lowercase\n    Unicode text\n    combining characters\n    punctuation\n    control characters\n    invalid values\n\nAlso test:\n\n    idempotence\n    determinism\n    field-specific policy\n\n## 39. Unit Test — Trim\n\n    assert trim_text("  PK  ") == "PK"\n\n## 40. Unit Test — Case\n\n    assert normalize_text("usd", case="upper") == "USD"\n\n## 41. Unit Test — Unicode\n\nUse accented characters, combining characters, and non-Latin scripts. Verify the selected Unicode normalization form produces the expected representation.\n\nDo not test only ASCII strings.\n\n## 42. Unit Test — Invalid Value\n\nFor a country code:\n\n    "P@K"\n\nmust not silently become:\n\n    "PK"\n\nThe value should fail semantic validation.\n\n## 43. Unit Test — Idempotence\n\n    value = "  pk  "\n    once = normalize_text(value, case="upper")\n    twice = normalize_text(once, case="upper")\n    assert once == twice\n\n## 44. Integration Test — Join Keys\n\nCreate:\n\n    left.country = "PK"\n    right.country = " pk "\n\nNormalize both sides and verify that the join matches according to the documented canonical key policy.\n\n## 45. Integration Test — Uniqueness\n\nIf the business contract says:\n\n    "ACME"\n    " ACME "\n\nrepresent the same key, canonicalize before applying the uniqueness rule.\n\nVerify that duplicates are handled according to the intended duplicate policy.\n\n## 46. Integration Test — Replay\n\nRun the same raw data twice.\n\nVerify:\n\n    identical canonical output\n    identical change count\n    no duplicate side effects\n\n## 47. Intentional Failure Drill — Global Lowercase\n\nTemporarily apply lowercase to every string field.\n\nTest case-sensitive identifiers and display names.\n\nObserve the corruption, remove the global rule, and replace it with field-specific policies.\n\n## 48. Intentional Failure Drill — ASCII Conversion\n\nTemporarily remove non-ASCII characters from multilingual names.\n\nObserve information loss.\n\nRestore Unicode preservation and add a regression test.\n\n## 49. Intentional Failure Drill — Punctuation Removal\n\nTemporarily remove all non-alphanumeric characters.\n\nUse identifiers such as AC-1001 and names such as O'Connor.\n\nObserve collisions or data changes.\n\nReplace the rule with an explicit field-specific policy.\n\n## 50. Intentional Failure Drill — Over-Normalization\n\nNormalize free text by lowercasing, collapsing whitespace, and removing punctuation.\n\nCompare the result with the source and identify lost meaning.\n\nMove aggressive matching logic to a derived search key instead.\n\n## 51. Intentional Failure Drill — Unicode Form\n\nCompare a representative dataset under NFC and NFKC.\n\nInvestigate changed values before selecting a production normalization form.\n\nThis demonstrates why compatibility normalization is not automatically harmless.\n\n## 52. Production Runbook\n\nWhen normalized values unexpectedly change:\n\n### Step 1 — Identify the field\n\nCheck source, dataset, field, and policy version.\n\n### Step 2 — Compare source and canonical state\n\nDetermine what changed and which rule changed it.\n\n### Step 3 — Check historical change rate\n\nCompare the current rate with previous runs.\n\n### Step 4 — Check source changes\n\nInspect producer deployments, schema changes, encoding changes, and new producers.\n\n### Step 5 — Determine impact\n\nIdentify affected joins, deduplication, uniqueness constraints, and downstream data.\n\n### Step 6 — Stop propagation when necessary\n\nIf the transformation causes data loss or collisions, stop the affected path.\n\n### Step 7 — Correct the field policy\n\nDo not fix the issue with another generic transformation.\n\n### Step 8 — Replay\n\nReplay from durable raw evidence.\n\n### Step 9 — Reconcile\n\nCompare record counts, changed-value counts, duplicate counts, and join results.\n\n### Step 10 — Add regression coverage\n\nLock the discovered edge case into CI.\n\n## 53. Recovery — Data Loss\n\nIf punctuation, Unicode characters, or case were incorrectly removed:\n\n1. Identify the affected policy version.\n2. Identify affected runs.\n3. Recover raw source values.\n4. Correct the normalizer.\n5. Replay.\n6. Rebuild affected derived keys.\n7. Reconcile downstream joins and duplicates.\n8. Add regression tests.\n\nPrefer replay from raw evidence over manual reconstruction.\n\n## 54. Recovery — Collision\n\nIf two distinct source values became the same normalized key:\n\n    value A -> key X\n    value B -> key X\n\nstop the affected deduplication path, recover the raw values, correct the comparison policy, rebuild derived keys, rerun matching, and reconcile downstream records.\n\nDo not assume the collision means the source records are duplicates.\n\n## 55. Recovery — Wrong Unicode Policy\n\nIf the wrong Unicode normalization form was used:\n\n1. Identify affected fields.\n2. Confirm the domain or protocol requirement.\n3. Restore the correct policy.\n4. Replay from raw evidence.\n5. Rebuild derived keys.\n6. Verify matching and uniqueness.\n\n## 56. Common Mistakes\n\n### Mistake 1 — One normalizer for every string\n\nFix: Define field-specific policies.\n\n### Mistake 2 — Lowercasing everything\n\nFix: Normalize case only where semantically safe.\n\n### Mistake 3 — Removing punctuation globally\n\nFix: Preserve meaningful punctuation.\n\n### Mistake 4 — Converting everything to ASCII\n\nFix: Preserve Unicode unless explicitly required otherwise.\n\n### Mistake 5 — Using normalization as validation\n\nFix: Normalize representation, then validate meaning.\n\n### Mistake 6 — Normalizing passwords or secrets\n\nFix: Treat them as exact values unless their protocol says otherwise.\n\n### Mistake 7 — Over-normalizing free text\n\nFix: Keep canonical business text conservative and use derived search keys when needed.\n\n### Mistake 8 — Normalizing only one join side\n\nFix: Apply the same canonical-key policy to both sides.\n\n### Mistake 9 — Ignoring idempotence\n\nFix: Test repeated normalization.\n\n### Mistake 10 — Ignoring Unicode\n\nFix: Include Unicode and combining-character tests.\n\n### Mistake 11 — Treating visual similarity as equality\n\nFix: Follow explicit identity and Unicode rules.\n\n### Mistake 12 — Hiding transformations\n\nFix: Measure normalization changes and version important policies.\n\n## 57. Production Tools You Should Know\n\n### Python\n\nUnderstand string trimming, regular expressions, casefolding, Unicode normalization, and UUID parsing.\n\n### PostgreSQL\n\nUnderstand text types, collations, indexes, unique constraints, and derived or expression-based keys.\n\n### Unicode Standard / UAX 15\n\nUnderstand Unicode normalization and the differences between NFC, NFD, NFKC, and NFKD. Use the applicable protocol or standard for security-sensitive processing.\n\n## 58. Design Principle — Normalize Conservatively\n\nEvery transformation should answer:\n\n> What semantic problem does this solve?\n\nIf the answer is only that the data looks cleaner, do not automatically put the transformation into the canonical pipeline.\n\n## 60. Design Principle — Canonicalize by Contract\n\nDocument:\n\n    input representation\n    output representation\n    transformation\n    validation\n    version\n\nConsumers must understand the same canonical representation.\n\n## 61. Design Principle — Preserve Original Meaning\n\nWhen aggressive normalization is required for search, matching, or deduplication, prefer a derived key instead of destroying the canonical value.\n\n## 62. Design Principle — Idempotence\n\nFor a canonical normalizer:\n\n    N(N(x)) = N(x)\n\nThis makes retry, replay, and backfill safer.\n\n## 63. Design Principle — Unicode Is Data\n\nNames, addresses, descriptions, and other human text can contain meaningful Unicode characters.\n\nPreserve them unless the contract explicitly requires another representation.\n\n## 64. Design Principle — Opaque Values Stay Opaque\n\nPasswords, tokens, signatures, API keys, and opaque idempotency keys should not pass through generic normalization.\n\n## 65.
