# Chapter 11 — Finding Database Code

Most Data Engineering pipelines eventually have to store, read, update, or delete data.

That usually means there is database code somewhere in the repository.

When investigating an existing pipeline, finding the database connection is only the beginning.

You also need to understand:

- Where connections are created
- Where queries are defined
- Where transactions begin and end
- Which functions read data
- Which functions write data
- Which tables are affected
- Which constraints protect the data
- Where migrations define the schema
- How tests create and clean up database state

This chapter teaches a practical method for finding and understanding database code in an unfamiliar Data Engineering repository.

---

# Why Database Investigation Matters

Suppose you receive this task:

> Add a unique constraint for incoming events.

You find a database connection file.

But that file does not tell you:

- Which table stores the events
- Which function inserts them
- Whether duplicates are already handled
- Whether the operation runs inside a transaction
- Which migration created the table
- Which tests cover duplicate events

Changing the wrong layer can create unnecessary code or break existing behavior.

A database investigation should connect the application code to the actual database structure.

---

# The Database Path

A useful mental model is:

~~~text
Pipeline entry point
       |
       v
Service / processor
       |
       v
Repository / database function
       |
       v
Database client
       |
       v
SQL / ORM operation
       |
       v
PostgreSQL
       |
       v
Table / index / constraint
~~~

**GENERIC EXAMPLE**

The names and layers vary between projects.

The investigation goal is to trace the complete path.

---

# Step 1 — Identify the Database

Start by determining which database technology the repository uses.

Look for:

- Dependency files
- Configuration
- Docker Compose services
- Docker images
- Connection URLs
- Client libraries
- Migration tooling
- ORM configuration

Common examples include:

- PostgreSQL
- MySQL
- MariaDB
- SQLite
- MongoDB
- Snowflake
- BigQuery
- ClickHouse

A repository may also use more than one storage system.

Do not assume that finding one database means you have found all persistence layers.

---

# Step 2 — Find the Database Connection

Search for the code that creates or obtains a database connection.

Common patterns include:

- Connection functions
- Connection pools
- ORM session factories
- Database clients
- Dependency injection
- Environment-based connection configuration

For PostgreSQL, generic code may conceptually look like:

~~~python
connection = connect(database_url)
~~~

**GENERIC EXAMPLE**

The actual repository may use a different client, framework, or connection pattern.

The important question is:

> Where does application code get access to the database?

---

# Connection Code Is Not Query Code

This distinction is important.

A connection module may only do this:

~~~text
Create connection
Create pool
Return client
~~~

It may contain no business queries at all.

After finding the connection, follow its callers.

Ask:

> Which code requests this connection?

Then:

> What does that code do with the connection?

That is how you move from infrastructure to database behavior.

---

# Step 3 — Find SQL

Search for SQL statements.

Common keywords include:

- `SELECT`
- `INSERT`
- `UPDATE`
- `DELETE`
- `UPSERT`
- `CREATE TABLE`
- `ALTER TABLE`
- `CREATE INDEX`

SQL may appear:

- Directly in Python or another language
- In separate `.sql` files
- Inside repository classes
- Inside migration files
- Inside stored procedures
- Generated by an ORM

Do not assume that searching for `SELECT` will find every database operation.

An ORM may generate SQL without storing the SQL statement directly in application code.

---

# Step 4 — Find the Repository Layer

Some projects use a repository or data-access layer.

Conceptually:

~~~text
Service
  |
  v
Repository
  |
  v
Database
~~~

The repository layer may contain functions such as:

- `get_event`
- `insert_event`
- `update_status`
- `find_pending_records`

These names are generic examples.

The exact structure depends on the project.

Repository layers can make database access easier to find, but not every codebase uses this pattern.

---

# Step 5 — Find ORM Models

An ORM maps application objects to database structures.

For example, a model may represent a table:

~~~text
Application model
       |
       v
Database table
~~~

A model may define:

- Table name
- Columns
- Data types
- Relationships
- Constraints

**GENERIC EXAMPLE**

If the repository uses an ORM, inspect both the model definitions and the generated database schema.

Do not assume that an ORM model is always identical to the production database schema.

Migrations, manual SQL, extensions, and deployment history can create differences.

---

# Step 6 — Find the Actual Write

Suppose you find a function called:

~~~text
save_event()
~~~

Do not stop there.

Find out:

1. Which table does it write to?
2. Which columns are written?
3. Is it an insert or update?
4. What happens on conflict?
5. Is it inside a transaction?
6. What happens if the write fails?
7. Does the caller retry it?
8. What does the function return?

The actual write path is what matters when changing database behavior.

---

# Insert Path

A generic insert path may look like:

~~~text
Event
  |
  v
Validate
  |
  v
Prepare database values
  |
  v
INSERT
  |
  v
Commit
~~~

**GENERIC EXAMPLE**

When investigating an insert, inspect every step around the SQL operation.

A bug may occur before the query, inside the query, or after the query.

---

# Update Path

An update path may look like:

~~~text
Existing record
      |
      v
Find record
      |
      v
Validate transition
      |
      v
UPDATE
      |
      v
Commit
~~~

**GENERIC EXAMPLE**

Updates are especially important when a pipeline uses processing states.

For example:

~~~text
RECEIVED
   |
   v
PROCESSING
   |
   v
COMPLETED
~~~

Find where those state changes are written.

---

# Step 7 — Find Transactions

Transactions are critical when investigating database behavior.

Look for:

- `BEGIN`
- `COMMIT`
- `ROLLBACK`
- Transaction context managers
- Session transaction methods
- Database transaction decorators

Conceptually:

~~~text
BEGIN
  |
  v
Operation A
  |
  v
Operation B
  |
  v
COMMIT
~~~

If an operation fails:

~~~text
BEGIN
  |
  v
Operation A
  |
  v
Operation B
  |
  X
ROLLBACK
~~~

**GENERIC EXAMPLE**

Understanding the transaction boundary is essential before adding retry behavior.

---

# Transaction Boundary

One of the most useful questions is:

> What exactly is inside the transaction?

Consider:

~~~text
BEGIN
  |
  +-- insert raw record
  +-- update processing state
  +-- write audit record
  |
COMMIT
~~~

That is different from:

~~~text
insert raw record
    |
COMMIT
    |
update processing state
    |
COMMIT
~~~

The failure and recovery behavior can be very different.

Do not infer transaction boundaries from function names.

Read the actual implementation.

---

# Step 8 — Find Connection Pools

Production systems often use connection pools.

A pool allows multiple operations to reuse a controlled set of database connections.

Conceptually:

~~~text
Workers
  |
  +----+----+----+
       |    |    |
       v    v    v
      Connection Pool
             |
             v
          Database
~~~

**GENERIC EXAMPLE**

When investigating database failures, determine whether the system uses individual connections or a pool.

This can affect:

- Connection exhaustion
- Concurrency
- Timeouts
- Retry behavior
- Resource usage

---

# Step 9 — Find Connection Configuration

Database connection settings may include:

- Host
- Port
- Database name
- Username
- Password
- SSL settings
- Pool size
- Connection timeout
- Command timeout

Secrets should normally come from secure configuration rather than source code.

When documenting a repository, record the configuration names and behavior without exposing credentials.

---

# Step 10 — Find the Table

Once you find a database operation, identify the actual table.

For example:

~~~text
store_event()
    |
    v
INSERT
    |
    v
telemetry_event
~~~

**GENERIC EXAMPLE**

Then search for the table name across the repository.

This can reveal:

- Migrations
- Indexes
- Constraints
- Tests
- Queries
- Reports
- Cleanup jobs
- Other writers

Searching by table name is one of the most effective repository investigation techniques.

---

# Step 11 — Find All Writers

Finding one write operation is not enough.

Ask:

> Who else writes to this table?

For example:

~~~text
                 +-- ingestion worker
                 |
table <----------+-- replay job
                 |
                 +-- backfill job
~~~

**GENERIC EXAMPLE**

Multiple writers can create unexpected behavior.

A new constraint or processing rule may affect all of them.

Before changing a table, search for every important writer.

---

# Step 12 — Find All Readers

Then ask:

> Who reads from this table?

Readers may include:

- Pipeline stages
- APIs
- Reports
- Data quality jobs
- Backfill scripts
- Analytics queries
- Monitoring jobs

A schema change that looks harmless to one writer may break a downstream reader.

Database investigation therefore includes both sides:

~~~text
Writers ---> Table ---> Readers
~~~

---

# Step 13 — Find the Migration

After identifying the table, find the migration that created it.

Look for:

- `CREATE TABLE`
- Table creation helpers
- Migration classes
- Versioned SQL
- Schema management commands

Read the creation migration first.

Then inspect later migrations that changed the table.

---

# Why the Migration History Matters

Suppose the current table contains:

~~~text
event_id
status
created_at
~~~

That tells you the current shape.

But migration history may tell you:

~~~text
Migration 1 -> table created
Migration 2 -> status added
Migration 3 -> index added
Migration 4 -> constraint changed
~~~

**GENERIC EXAMPLE**

This history explains why the schema looks the way it does.

It can also explain compatibility decisions in application code.

---

# Step 14 — Find Indexes

Indexes affect both correctness and performance.

Search for:

- Primary keys
- Unique indexes
- Normal indexes
- Composite indexes
- Partial indexes

For example, if the pipeline frequently searches by:

~~~text
event_id
~~~

you should determine whether the database has an appropriate lookup structure.

Do not add indexes blindly.

Understand the query pattern first.

---

# Step 15 — Find Constraints

Constraints can enforce data rules at the database layer.

Look for:

- Primary keys
- Unique constraints
- Foreign keys
- NOT NULL constraints
- CHECK constraints

These constraints may be important parts of the pipeline's data quality and idempotency design.

For example:

~~~text
Application
    |
    v
Database constraint
    |
    v
Stored data
~~~

A constraint can protect the database even if an application code path misses a validation check.

---

# Step 16 — Find Foreign Keys

Foreign keys show relationships between tables.

For example:

~~~text
customers
    |
    | customer_id
    v
orders
~~~

**GENERIC EXAMPLE**

When changing a table, understand these relationships.

A delete, update, or schema change may affect related records.

---

# Step 17 — Find Database Functions and Triggers

Some repositories use database-side logic.

Look for:

- Functions
- Procedures
- Triggers
- Views
- Materialized views

Not every project uses them.

But if they exist, application code may not contain the complete behavior.

For example:

~~~text
Application INSERT
       |
       v
Database trigger
       |
       v
Audit table
~~~

**GENERIC EXAMPLE**

Always investigate database-side behavior when debugging unexpected database changes.

---

# Step 18 — Find Tests That Touch the Database

Database tests are especially valuable.

Look for:

- Integration tests
- Repository tests
- Database fixtures
- Temporary database setup
- Migration tests
- Transaction tests
- Constraint tests

A test may show exactly how the repository expects the database to behave.

---

# Unit Tests vs Integration Tests

A unit test may mock the database.

Conceptually:

~~~text
Function
  |
  v
Mock database
~~~

An integration test may use a real database:

~~~text
Function
  |
  v
Real PostgreSQL
~~~

**GENERIC EXAMPLE**

Both are useful.

A mocked test can verify application logic quickly.

A real database test can verify SQL, constraints, transactions, and integration behavior.

---

# Find Database Fixtures

Tests often need initial database state.

Look for:

- Fixture functions
- Seed data
- SQL setup files
- Test migrations
- Factory functions
- Temporary database creation

Fixtures can tell you which records the application considers valid or important.

---

# Find Database Cleanup

Tests may need to clean up database state.

Look for:

- Rollbacks
- Truncation
- Transaction fixtures
- Temporary schemas
- Database recreation

This matters because test isolation can affect whether duplicate or state-related tests are reliable.

---

# Follow One Database Operation

A powerful technique is to trace one operation from the pipeline to the database.

Suppose the task is:

> Find where an event is stored.

Start with:

~~~text
event arrives
     |
     v
handler
     |
     v
processor
     |
     v
repository
     |
     v
SQL
     |
     v
table
~~~

**GENERIC EXAMPLE**

Write down each step.

If you cannot explain the path, keep investigating.

---

# Follow One Database Failure

Suppose the error is:

~~~text
duplicate key violation
~~~

Trace backward:

~~~text
Database error
     |
     v
SQL operation
     |
     v
Repository function
     |
     v
Processing function
     |
     v
Input event
~~~

Then ask:

- Why was the same key written?
- Is the key supposed to be unique?
- Is duplicate handling expected?
- Is the write retried?
- Is the operation idempotent?
- Is there a race condition?

This connects the database error to pipeline behavior.

---

# Check-Then-Insert Race Conditions

A common database investigation problem is code that does:

~~~text
Check if record exists
        |
        v
Record does not exist
        |
        v
Insert record
~~~

This looks safe.

But two workers can execute the check at the same time.

~~~text
Worker A -> check -> not found
Worker B -> check -> not found
Worker A -> insert
Worker B -> insert
~~~

Depending on the schema and operation, this can produce duplicate data or a constraint error.

This is one reason database constraints and atomic operations matter.

---

# Upsert

An upsert combines insert and conflict handling into one database operation.

Conceptually:

~~~text
Insert
  |
  +---- no conflict ----> store
  |
  +---- conflict -------> update / ignore
~~~

**GENERIC EXAMPLE**

PostgreSQL supports several forms of conflict handling.

The exact query should be designed according to the intended semantics.

Do not use an upsert simply because it is available.

Decide what a duplicate should mean first.

---

# Transactions and Retry

When investigating retry behavior, always find the transaction boundary.

Consider:

~~~text
BEGIN
  |
  v
INSERT
  |
  v
COMMIT
~~~

If the insert fails before commit, retrying the transaction may be safe depending on the operation.

If an external side effect happens before the transaction, retrying may have different consequences.

The database code must be understood together with the surrounding pipeline code.

---

# Database Connection Failures

Connection failures can happen because of:

- Database outage
- Network problems
- Connection exhaustion
- Invalid configuration
- Authentication problems
- TLS problems
- Timeouts
- Database restart

Find where these errors are handled.

Ask:

- Is there retry logic?
- Who owns the retry?
- Is the connection recreated?
- Is the transaction rolled back?
- Is processing state updated?
- Is the failure visible in logs or metrics?

---

# Connection Pool Exhaustion

Suppose the application has a limited connection pool.

If too many operations hold connections for too long, new operations may wait or fail.

Conceptually:

~~~text
Worker A -> connection 1
Worker B -> connection 2
Worker C -> connection 3
Worker D -> waiting
Worker E -> waiting
~~~

**GENERIC EXAMPLE**

During investigation, look at:

- Pool configuration
- Connection lifetime
- Transaction duration
- Unclosed connections
- Concurrency

Do not assume a database outage is the cause when the real problem may be application-side connection exhaustion.

---

# Read the SQL Before Changing It

When a ticket concerns database behavior, read the actual query.

Ask:

- Which table does it touch?
- Which columns does it use?
- Which filters are applied?
- Which indexes support those filters?
- Is it inside a transaction?
- Can it return duplicate rows?
- Can it update more records than expected?
- What happens when no rows match?

SQL often contains important behavior that is easy to miss from function names alone.

---

# Query Parameters

Database queries should normally use parameterized values rather than building SQL by string concatenation.

Conceptually:

~~~text
SQL template
    +
Parameters
    |
    v
Database driver
~~~

**GENERIC EXAMPLE**

Parameterized queries help separate SQL structure from user or pipeline data and reduce SQL injection risk.

Follow the actual database library's parameterization mechanism.

---

# Database Code and Sensitive Data

Database investigation may expose sensitive fields.

Be careful with:

- Personal information
- Authentication data
- Financial information
- Documents
- Tokens
- Secrets

Do not copy sensitive production values into tickets or documentation unless there is an approved reason to do so.

When demonstrating database behavior, use synthetic examples.

---

# Repository Investigation Example

Imagine a task says:

> Duplicate telemetry events are appearing in the database.

Use the following investigation sequence.

### Step 1 — Find the event entry point

Where does the event enter the pipeline?

### Step 2 — Follow processing

Which function prepares the event for storage?

### Step 3 — Find the database write

Which function performs the insert?

### Step 4 — Find the table

Which table stores the event?

### Step 5 — Find the identifier

Which column identifies the logical event?

### Step 6 — Find constraints

Is that identifier unique?

### Step 7 — Find duplicate handling

Does the SQL use conflict handling?

### Step 8 — Find transaction behavior

Could concurrent workers perform the same insert?

### Step 9 — Find tests

Is duplicate processing tested?

### Step 10 — Find other writers

Could another process be inserting the same records?

Now the investigation covers the full database path rather than one SQL statement.

# Common Mistakes

## Mistake 1: Finding only the connection code

A connection does not tell you where data is written.

Follow the connection to the actual operations.

## Mistake 2: Reading only application code

Database migrations and constraints may contain important behavior.

## Mistake 3: Reading only the ORM model

The actual database schema may also depend on migrations and manual SQL.

## Mistake 4: Ignoring transactions

Transaction boundaries affect failure and retry behavior.

## Mistake 5: Ignoring other writers

Another process may write to the same table.

## Mistake 6: Ignoring indexes

A query can be logically correct but operationally expensive.

## Mistake 7: Ignoring tests

Tests often reveal database expectations.

## Mistake 8: Changing schema without migration history

You may break compatibility with existing data or deployments.

## Mistake 9: Assuming duplicate errors are always bad

A duplicate may be an expected race or replay condition that should be handled deliberately.

## Mistake 10: Copying production data into debugging material

Use identifiers and synthetic examples instead of unnecessary sensitive values.

# Production Considerations

When investigating production database behavior, identify:

- Database technology
- Connection mechanism
- Pool configuration
- Transaction boundaries
- Query paths
- Tables affected
- Indexes
- Constraints
- Foreign keys
- Database-side functions or triggers
- Migration history
- Retry behavior
- Timeout behavior
- Monitoring
- Backup and recovery strategy

Also identify whether the operation can safely be repeated.

This matters for retries, replay, and backfills.

---

# Practical Checklist

Before changing database-related code in an unfamiliar repository, ask:

- [ ] Do I know which database is involved?
- [ ] Do I know where the connection is created?
- [ ] Do I know how configuration reaches the connection?
- [ ] Do I know whether a connection pool is used?
- [ ] Have I found the relevant SQL or ORM operation?
- [ ] Do I know which table is affected?
- [ ] Have I found all important writers?
- [ ] Have I found important readers?
- [ ] Have I found the table-creation migration?
- [ ] Have I checked later migrations?
- [ ] Have I inspected indexes?
- [ ] Have I inspected constraints?
- [ ] Have I inspected foreign keys?
- [ ] Have I checked for triggers or database-side logic?
- [ ] Do I understand the transaction boundary?
- [ ] Do I understand failure and retry behavior?
- [ ] Have I found database-related tests?
- [ ] Do I understand test database setup?
- [ ] Have I considered duplicate and concurrent processing?
- [ ] Have I checked for sensitive data handling?

# What You Learned

In this chapter, you learned:

- Database investigation starts by identifying the storage technology.
- Finding the connection is only the first step.
- You should trace database access to the actual query or ORM operation.
- Repository or data-access layers can make database behavior easier to locate.
- ORM models are useful but should be checked against migrations and the actual schema.
- Transactions define important failure boundaries.
- Connection pools affect concurrency and database behavior.
- Searching by table name can reveal writers, readers, migrations, tests, and indexes.
- Constraints are part of the application's data correctness strategy.
- Database-side logic such as triggers and functions can affect behavior.
- Database tests provide valuable evidence about expected behavior.
- Duplicate and concurrent processing require careful database investigation.
- Production database changes should be understood together with migration and recovery behavior.

The main lesson is:

**Do not stop when you find the database connection. Trace the complete path from pipeline code to query to table to schema, constraints, and tests. That is where the real database behavior lives.**
